# 🧾 LINE Slip Bot — รวมยอดสลิปรายคน + ค่าคอมมิชชั่น

ที่มา: สรุปจากการคุยวางแผน 1–3 ต.ค. 2026 ที่ผู้ใช้แปะเข้ามาเป็น context โปรเจกต์ — รายละเอียดเชิงเทคนิคทั้งหมด (stack, architecture, flow, design rules, data model, ต้นทุน, deploy, ลำดับ MVP) อยู่ที่ [[Design Spec]] โน้ตนี้เก็บเฉพาะมุมตัดสินใจ: ปัญหา / สมมติฐาน / prior art / การทดลอง / ความเสี่ยง

## 🎯 ปัญหา

ทีมขาย / แม่ทีมตัวแทน / ร้านที่มีแอดมินปิดการขายหลายคน ส่งรูปสลิปเข้ากลุ่ม LINE ทุกวัน สิ้นเดือนเจ้าของต้องนั่งไล่รวมยอดทีละรูปเพื่อคิดค่าคอม → เสียเวลา, ผิดง่าย, ทะเลาะเรื่องเงิน และไม่รู้ว่าสลิปไหนปลอมหรือถูกส่งซ้ำ

**ควรตอบให้ชัดก่อนขยับจาก `seed`: ทำไปเพื่ออะไร** — เพราะมันเปลี่ยน "การทดลองที่เล็กที่สุด" ทั้งหมด (แพทเทิร์นเดียวกับที่เคยตั้งคำถามนี้ใน [[URL Shortener (Quarkus)]] และ [[Background Job Processor (Quarkus)]]) ตัวเลือกที่เห็น (ร่างเพิ่มตอนบันทึก — **ยังไม่ได้เลือก**):

1. ทำเป็นโปรดักต์ขายจริง (เก็บเงินต่อกลุ่ม/ต่อสลิป) — เนื้อหาต้นทางเอนมาทางนี้ (มีคู่แข่ง, ราคาขาย, ลูกค้า) แต่ยังไม่มีใครยืนยัน
2. ทำใช้เอง/ให้คนรู้จักใช้ ไม่ขาย
3. ทำเพื่อฝึกทักษะ (LINE bot + ตรวจสลิป + AI + deploy จริง) โดยตัวโปรดักต์เป็นแค่โจทย์

## 💭 สมมติฐาน

- เชื่อว่าความเจ็บ (รวมยอดสิ้นเดือน, สลิปซ้ำ/ปลอม, ทะเลาะเรื่องเงิน) หนักพอที่ทีมที่มีลูกทีมราว 5–10 คนจะยอมเปลี่ยนมาใช้บอทที่อยู่ในกลุ่ม LINE เดิม **โดยไม่ต้องเปลี่ยนพฤติกรรมการส่งสลิป**
- เชื่อว่า "เริ่มจากปัญหาเดียวที่เจ็บจริง" ชนะ "ทำ ERP ทั้งชุดก่อน" เพราะไม่ต้องแข่งกับเจ้าใหญ่ทุกด้าน (ลำดับขยายที่คิดไว้: ตรวจสลิป → ค่าใช้จ่าย → กำไรขาดทุน → สต็อก/เงินเดือน)
- เชื่อว่าจุดแข็งที่คู่แข่งตามยาก = ความเข้าใจกติกาค่าคอมของกลุ่มลูกค้านี้ลึกกว่า + เข้าตลาดก่อน (ต้นทางยอมรับว่า Paypers/Thunder มีพื้นฐานพอจะเพิ่มฟีเจอร์นี้ได้)

**ถ้าสมมติฐานผิด จะรู้จาก validation (🧪 ข้อ A):** เจ้าของ/แม่ทีมไม่เจ็บพอ, ใช้เครื่องมือเดิมแก้ได้พอแล้ว, ไม่ยอมจ่าย, หรือกติกาค่าคอมของแต่ละเจ้าต่างกันมากจนทำเป็นผลิตภัณฑ์เดียวไม่ได้ (ร่างเพิ่มตอนบันทึก)

## ❓ ทำไมต้องตอนนี้

(ยังไม่ได้ตอบ — โน้ตต้นทางไม่ได้ระบุเหตุผลเชิงเวลา) เบาะแสเดียวคือความเสี่ยงที่คู่แข่งเพิ่มฟีเจอร์นี้ → "เข้าตลาดก่อน" ซึ่งเป็นข้อโต้แย้งเรื่องความรีบที่ยังไม่ได้ตรวจสอบ ถ้าตอบไม่ได้ ไม่ผิด — แปลว่าไม่รีบ

## 🧱 Design ที่เสนอ

บอท LINE อยู่ในกลุ่มที่ทีมใช้อยู่แล้ว: รับรูปสลิป → รู้ว่าใครส่ง (LINE `userId`) → อ่านยอด + ตรวจสลิปจริง/ปลอม/ซ้ำ → รวมยอดรายคนรายเดือน → คำนวณค่าคอมเป็น % (อนาคต: ขั้นบันได) → พิมพ์ "สรุปเดือนนี้" ในแชทให้บอทตอบ + หน้าเว็บแอดมินสำหรับดูยอด/ปิดเดือน

ภาพรวม stack: Quarkus + Supabase (ใช้แค่ Postgres + Storage ผ่าน Quarkus เท่านั้น) + LINE Messaging API + ZXing อ่าน QR + ตรวจสลิปผ่าน interface `SlipVerifier` (สลับเจ้าได้) + Gemini เป็น fallback สำหรับบิลที่ไม่ใช่สลิป (คนต้องกดยืนยันเสมอ) + Angular admin + VPS/Docker Compose/Cloudflare Tunnel

กฎที่ต้องไม่ละเลย 3 ข้อจาก 11 ข้อ: เงินไม่ใช้ `double` · กันซ้ำที่ DB ด้วย `UNIQUE` · AI อ่านยอดต้องให้คนกดยืนยัน — **ทั้ง 11 ข้อ + data model + flow + ต้นทุน + deploy → [[Design Spec]]**

- เวลารวมยอดสิ้นเดือน จาก [X ชม.] เหลือแค่เวลาตรวจทานผล [Y นาที]
- สลิปซ้ำ/ปลอมถูกจับได้ตอนส่งเข้ากลุ่ม ไม่ใช่ตอนสิ้นเดือน — วัดด้วยชุดสลิปทดสอบที่รู้เฉลยแล้ว
- ยอดรวมรายคนที่บอทสรุปตรงกับที่แม่ทีมนับเองในเดือนทดลอง (เทียบสองทาง)

## 🧪 การทดลองที่เล็กที่สุด

**ข้อเสนอ (ยังไม่ยืนยัน) — ไม่ทำ Angular admin / ปิดเดือน / ค่าคอมขั้นบันได / Gemini ก่อน** เพราะความเสี่ยงจริงของโปรเจกต์นี้อยู่ที่ (ก) ปัญหานี้เจ็บจริงไหม และ (ข) flow หลัก "สลิปใน LINE → รู้คน → รู้ยอด → รู้ว่าจริง" ทำได้แม่นแค่ไหน ไม่ใช่หน้าจอ admin ซึ่งเป็นงานที่คุ้นมืออยู่แล้ว ทางที่เลือกขึ้นกับคำตอบเรื่อง "ทำไปเพื่ออะไร" ด้านบน:

**A. ทดสอบว่าปัญหาจริงไหม — ไม่ต้องเขียนโค้ด (ไม่กี่วัน)** — เหมาะถ้าตั้งใจทำเป็นโปรดักต์

- [ ] คุยกับแม่ทีม/เจ้าของร้านที่มีลูกทีมขาย 5–10 คน 2–3 คน: ตอนนี้รวมยอด/คิดคอมยังไง ใช้เวลาเท่าไหร่ เคยโดนสลิปปลอมไหม จะยอมจ่ายเท่าไหร่
- [ ] ถามว่าใช้ป้านวล/Paypers/อื่นๆ อยู่ไหม ทำไมยังต้องรวมยอดเอง
- [ ] ลองใช้บอท Thunder จริง ดูว่าแยกยอดรายคนได้หรือไม่
- ไปต่อถ้า: มีอย่างน้อยหนึ่งคนที่เล่าว่าเจ็บจริง (เสียเวลา/เคยโดนปลอม) และยอมคุยเรื่องราคา · พอถ้า: ทุกคนใช้เครื่องมือเดิมอยู่แล้วหรือไม่เจ็บ (ร่าง — ปรับได้)

**B. ทดสอบว่า flow หลักทำได้จริงไหม — สไปก์ทางเทคนิค ไม่มี DB/คิว/UI (วันเสาร์เดียว)** — เหมาะถ้าตั้งใจฝึกทักษะ หรือถ้า A ผ่านแล้ว

1. **B1 — สลิป → ยอดที่เชื่อได้:** สลิปจริง 5–10 ใบจากหลายธนาคาร (เจาะกรุงศรีตามที่ต้นทางแนะนำ) ที่ **ส่งผ่านกลุ่ม LINE แล้วโหลดกลับมา** (ไม่ใช่ไฟล์ต้นฉบับ) → ZXing อ่าน QR → parse TLV (tag `00` ซ้อน, `51`, `91` CRC) → เรียก Thunder Free → print `transRef`/ยอด/ผู้รับ ผ่านถ้าอ่านและตรวจได้ครบทุกธนาคารที่ทดสอบ · ไม่ผ่านถ้าธนาคารไหนอ่าน QR ไม่ออก (สมมติฐานเรื่องความแม่นของ flow หลักต้องเปลี่ยน)
2. **B2 — webhook ได้ `userId` จริงไหม:** ทำ webhook เปล่าที่ log event ลงไฟล์ (เปิดด้วย Cloudflare quick tunnel ตาม [[Cloudflare]] ข้อ 5 + LINE OA Free) ให้สมาชิกส่งรูปเข้ากลุ่มทดสอบจาก iOS/Android/**LINE Desktop** และคนที่ไม่เคยแอดบอท ดูว่า `userId` มาครบไหม — เป็นสมมติฐานที่ชนแก่นของโปรดักต์ (ยอดรายคน) ตรงๆ (ดู ⚠️ ข้อแรกที่เพิ่มตอนบันทึก)

## ⚠️ ความเสี่ยง / สิ่งที่อาจทำให้พัง

**จากโน้ตต้นทาง:**

- Paypers/Thunder มีพื้นฐานพอจะเพิ่มฟีเจอร์นี้ได้ → จุดแข็งต้องมาจากความเข้าใจกติกาค่าคอมลึกกว่า + เข้าตลาดก่อน
- รูปส่วนใหญ่อาจเป็นบิล/ใบเสร็จมากกว่าสลิปโอน (สลิปแม่นกว่ามาก) — ยังไม่รู้
- ส่งสลิปลูกค้าจริงผ่าน Gemini free tier = ข้อมูลถูกใช้ปรับปรุงผลิตภัณฑ์ของ Google → ผิดหลัก PDPA ต้องผูก billing
- Supabase Free tier ไม่มี backup + pause หลังเงียบ 1 สัปดาห์ → ใช้กับข้อมูลทดสอบเท่านั้น
- Push เป็นต้นทุนที่โตเร็วที่สุด · ราคา/โควตาผู้ให้บริการเปลี่ยนได้ · Gemini Flash 3.6–3.8 ขึ้นราคา 2 เท่าตั้งแต่ 1 ม.ค. 2027

**เพิ่มตอนบันทึก (ไม่ได้มาจากโน้ตต้นทาง — ข้อ 1–3 ยังไม่ได้ทดสอบจริง รายละเอียดอยู่ใน [[Design Spec]] ข้อ 3.1 และ 4.1):**

- **`userId` ของคนส่งอาจหายไปจาก webhook ในกลุ่ม** — เอกสาร LINE ระบุว่ามีเฉพาะ message event และเฉพาะผู้ใช้ LINE for iOS/Android + มีเรื่อง consent → คนที่ส่งจาก LINE Desktop อาจจับคู่ "สลิป → คน" ไม่ได้ กระทบแก่นของโปรดักต์ตรงๆ (ทดสอบด้วย 🧪 B2)
- **replyToken ใช้ได้ครั้งเดียวและต้องใช้ภายใน 1 นาที** ชนกับกฎ "async + ใช้ reply ไม่ใช้ push" → ข้อความยืนยันที่ส่งหลังประมวลผลอาจต้อง push ซึ่งเปลี่ยนตัวเลขต้นทุนทั้งก้อน
- **webhook อาจถูกส่งซ้ำ (redelivery)** — ต้อง dedupe ด้วย `webhookEventId` ที่ตารางคิว ไม่ใช่แค่ `UNIQUE` ที่ `trans_ref`/`image_hash` (หลักการ [[Idempotency]])
- **`UNIQUE` ระดับ global ข้ามร้าน** — ร้าน B ที่ลงสลิปซ้ำกับร้าน A จะรู้ว่าสลิปนี้เคยถูกลงที่อื่น และ `trans_ref` อาจต้องคู่กับธนาคารถึงจะ unique จริง — ต้องเลือกระดับ unique ก่อนมีหลายร้าน
- **สลิปคือข้อมูลส่วนบุคคล** (ชื่อ, เลขบัญชีบางส่วน) ที่ถูกเก็บใน Supabase Storage และส่งต่อผู้ให้บริการภายนอก — PDPA ไม่ได้มีแค่เรื่อง Gemini free tier ต้องมี retention + แจ้งสมาชิกในกลุ่ม

## 📚 ต้องไปเรียนรู้เพิ่ม

- LINE Messaging API: signature (`X-Line-Signature`), Content API ดึงรูปด้วย `message.id`, reply vs push, Flex Message + postback, LINE Login สำหรับแอดมิน ([[OAuth 2.0]])
- Mini-QR บนสลิป: โครงสร้าง TLV (tag `00` ซ้อน, `51`, `91` CRC) — ต่อยอดจาก [[Thai QR Payment]] ข้อ 2 (CRC ของ tag 91 ยังไม่ได้ยืนยันว่าอัลกอริทึมเดียวกัน)
- ZXing อ่าน mini-QR จากรูปที่ผ่านกลุ่ม LINE ได้แม่นแค่ไหน (ต้องทดสอบกับสลิปจริงที่ส่งผ่านกลุ่ม — 🧪 B1)
- เทียบความแม่นผู้ให้บริการตรวจสลิป (Thunder / EasySlip / SlipOK) โดยเฉพาะกรุงศรี
- claim คิวด้วย `FOR UPDATE SKIP LOCKED` — โปรเจกต์ [[Background Job Processor (Quarkus)]] เป็นสนามฝึกตรงๆ
- Gemini API: structured output (JSON schema), `usageMetadata`, ความต่าง free tier vs billing (PDPA)
- Supabase ใช้แค่ Postgres + Storage ผ่าน Quarkus + RLS ([[Supabase]]), Flyway กับ Supabase ([[Quarkus Flyway]])
- คำถามที่ยังเปิดจากต้นทางทั้งหมด → [[Design Spec]] ข้อ 11

- **สถานะตั้งต้น `seed`** — มี prior art แล้ว แต่ยังไม่ได้ validate กับผู้ใช้จริง และยังไม่ได้ตอบว่า "ทำไปเพื่ออะไร" (ขายจริง/ใช้เอง/ฝึกทักษะ) ← ต้องตอบก่อนขยับเป็น `sprouting` (ตามแพทเทิร์นเดียวกับโน้ตอื่น)
- ค้นเอกสาร LINE ปิดคำถามค้างจากต้นทางได้ 2 ข้อ (ผลจากเอกสาร ยังไม่ได้ทดสอบจริง): (1) replyToken ใช้ได้ครั้งเดียวและต้องใช้ภายใน 1 นาทีหลังรับ webhook (เปลี่ยนได้โดยไม่แจ้ง) (2) `userId` ในกลุ่มมีเฉพาะ message event และเฉพาะผู้ใช้ LINE for iOS/Android + มีเงื่อนไข consent → ผู้ส่งจาก LINE Desktop อาจไม่มี `userId`
- เพิ่มข้อสังเกตที่ไม่ได้มาจากต้นทาง (แยกป้ายไว้ชัดเจนใน [[Design Spec]]): replyToken ชนกฎ async/reply, webhook redelivery ต้อง dedupe ด้วย `webhookEventId`, `UNIQUE` ระดับ global vs ต่อกลุ่ม, หน่วยสตางค์/บาทปนในสคีมา, คิดค่าคอมจากยอดรวมครั้งเดียว (ตัวอย่างรันจริง 926.00 vs 925.88)
- โค้ด Java 2 ชิ้นในสเปค (คำนวณค่าคอม, `SlipVerifier`) คอมไพล์และรันผ่านบน JDK 17
- เสนอการทดลองเล็กสุด 2 ทาง (A ทดสอบปัญหา / B สไปก์เทคนิค) — **ยังไม่ยืนยันร่วมกัน**
- ยังไม่ได้ตอบ: ทำไปเพื่ออะไร, ขยับ status หรือยัง, เห็นด้วยกับข้อเสนอการทดลอง A/B ไหม
